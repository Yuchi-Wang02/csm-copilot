# Limits and data handling

This is an educational portfolio prototype with synthetic records, not a deployable customer-support product.

- **No real account integration.** JSON fixtures represent a fixed snapshot. No CRM, Unity dashboard, ticketing or messaging connection exists.
- **Dependency enforcement is host-specific.** The optional [morning-review policy](DEPENDENCY_POLICY.md) rejects premature, duplicate and out-of-scope calls and supplies pending-action state each turn. Optional decoding schemas restrict generation to one pending action. The first constrained morning recording completes seven calls but times out before final prose; later recordings return answers, including matching fields after supplied correction feedback. The host supplies the allowed plan and IDs retrieved from tool results. This is assisted execution, not unaided planning, and the policy does not apply to arbitrary MCP clients.
- **Model evidence is exploratory.** Nineteen local attempts cover four prescribed synthetic tasks, including nine morning reviews, under changing prompts, response contracts and generation settings. The [recorded sequence](LOCAL_MODEL.md) preserves parsing failures, a timeout, incomplete explanations and rejected readiness citations. The eighth morning attempt repairs one citation after host feedback supplies the expected list; its 52-word explanation remains unchanged. The ninth adds an explanation checklist and again needs supplied feedback for that citation. Its 48-word explanation still omits platform next actions and source citations. The constrained platform-follow-up fields likewise match only after two corrections supplying expected values. Free prose remains unverified; matching fields do not establish source truth or full instruction compliance. These are inspected development cases, not independent evaluation, a model ranking, general reliability evidence or a controlled latency benchmark. The website replays recordings.
- **Local runtime can stop before an answer.** The constrained morning run reaches the existing 180-second response timeout after seven successful calls. Its raw trace retains the returned turns and `ExceptionGroup`, but that host version did not persist the final in-flight request or the nested timeout detail. A separate agent-authored terminal observation records the captured `TimeoutError`. The current host saves requests before dispatch and records specific response failures, with scripted integration checks. A subsequent 600-second-budget run returns a final explanation after 272.986 seconds of generation, but its prose still has evidence-state and task-completeness gaps. No missing historical response is reconstructed, and recorded timing is not a controlled performance benchmark.
- **Triage is a baseline.** Lexical matches can miss paraphrases and misread negation. Bounded rules exclude selected explicit no-offers and callback denials while preserving other occurrences; qualified negation, quoted topics and unsupported callback-denial forms still fail. Multiple symptoms are returned as candidates. The current [callback-denial replay](../evidence/CALLBACK_DENIAL.md) retains two authored mismatches, `qualified` and `quoted`. The [present-tense repair](CALLBACK_HEALTH.md) changed the former `not_failing` mismatch; its original result remains in the frozen evidence. These are inspected development cases, not an independent benchmark.
- **Evidence is attributed, not independently verified.** Account, integration, check scope and structured-claim agreement are validated. The system does not verify that claims match source prose or external truth, verify screenshots, automatically resolve contradictory evidence, or expire stale evidence. Conflicting records can remain explicitly unknown.
- **Checklist scope is partial.** `checklist_complete` covers six project checks and never certifies production launch, compliance or revenue.
- **Promise lint is narrow.** Regex patterns have both false positives and false negatives. Absence of flags never establishes factuality.
- **Evaluation is synthetic and same-session authored.** Family separation helps prevent bilingual duplicate leakage but does not create independent human validation. The current 16/18 replay follows adaptation to inspected failures; the original 14/18 result is preserved and neither is an independent quality estimate.
- **Drafting is read-only.** No records are sent or contact timestamps updated. A future write integration needs explicit authorization, review, idempotency and audit history.
- **No measured business outcome.** Time savings, resolution speed, activation rate and customer satisfaction are hypotheses for a future study.
- **Product feedback is a hypothesis.** `friction_digest` aggregates scoped checklist states, not automatically discovered customer-confusion themes. Distinct account counts overlap across themes. A repeated evidence gap does not establish a product defect, cause, priority or weekly trend.

## Handling customer text

Customer and sales messages are evidence data. Their contents cannot grant permissions or override tool rules. The server does not execute text, visit customer URLs or expose a shell. The bundled injection case verifies deterministic behavior only; it is not proof that every MCP host resists prompt injection.

## Before a real pilot

Use separately authorized, appropriately redacted data. Define access control, data retention, consent, evidence freshness and conflict handling. Evaluate against independently authored cases and human review. Keep a clear separation between draft creation and actual sending. These are future requirements, not claims of implemented production controls.
