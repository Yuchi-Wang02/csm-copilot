# Limits and data handling

This is an educational portfolio prototype with synthetic records, not a deployable customer-support product.

- **No real account integration.** JSON fixtures represent a fixed snapshot. No CRM, Unity dashboard, ticketing or messaging connection exists.
- **Model evidence is exploratory.** Ten local attempts cover three prescribed tasks under changing prompts, response contracts and generation settings. The constrained platform-follow-up fields match after two corrections that supply expected values. Free prose remains unverified; matching fields do not establish source truth or full instruction compliance. This is not independent evaluation, a model ranking or general reliability evidence. The website replays recordings.
- **Triage is a baseline.** Lexical matches can miss paraphrases and misread negation. Bounded rules exclude selected explicit no-offers and callback denials while preserving other occurrences; qualified negation, quoted topics and unsupported callback-denial forms still fail. Multiple symptoms are returned as candidates. The [callback-denial probes](../evidence/CALLBACK_DENIAL.md) include three preserved failures; they are development cases, not an independent benchmark.
- **Evidence is attributed, not independently verified.** Account, integration, check scope and structured-claim agreement are validated. The system does not verify that claims match source prose or external truth, verify screenshots, automatically resolve contradictory evidence, or expire stale evidence. Conflicting records can remain explicitly unknown.
- **Checklist scope is partial.** `checklist_complete` covers six project checks and never certifies production launch, compliance or revenue.
- **Promise lint is narrow.** Regex patterns have both false positives and false negatives. Absence of flags never establishes factuality.
- **Evaluation is synthetic and same-session authored.** Family separation helps prevent bilingual duplicate leakage but does not create independent human validation. The current 16/18 replay follows adaptation to inspected failures; the original 14/18 result is preserved and neither is an independent quality estimate.
- **Drafting is read-only.** No records are sent or contact timestamps updated. A future write integration needs explicit authorization, review, idempotency and audit history.
- **No measured business outcome.** Time savings, resolution speed, activation rate and customer satisfaction are hypotheses for a future study.
- **Product feedback is a hypothesis.** `friction_digest` aggregates scoped checklist states, not automatically discovered customer-confusion themes. Distinct account counts overlap across themes. A repeated evidence gap does not establish a product defect, cause, priority or weekly trend.

## Handling customer text

Customer and sales messages are evidence data. Their contents cannot grant permissions or override tool rules. The server does not execute text, visit customer URLs or expose a shell. The bundled injection case verifies deterministic behavior only; it is not proof that every MCP host resists prompt injection.

## Before a real pilot

Use separately authorized, appropriately redacted data. Define access control, data retention, consent, evidence freshness and conflict handling. Evaluate against independently authored cases and human review. Keep a clear separation between draft creation and actual sending. These are future requirements, not claims of implemented production controls.
